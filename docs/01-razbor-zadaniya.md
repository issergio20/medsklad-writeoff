# Списание материалов со склада — разбор тестового задания

> Позиция: Product Designer. Источник: Google Doc «Тестовое: Списание материалов со склада».
> Срок: 5 календарных дней. Бюджет: 4–6 часов. Сдаём: Figma (view-доступ) + пояснения + одностраничник решений + тайминг + источники/нейросети.

---

## 0. Суть в одном абзаце

Это задание не про форму, а про **конфликт интересов**. Кладовщик хочет списать быстро и одним документом. Старшая медсестра хочет, чтобы учётные материалы нельзя было списать мимоходом. Бухгалтеру нужна осмысленная причина у каждой строки. Сейчас все трое проигрывают из‑за причины «Прочее»: честный путь (5 документов на 5 причин) стоит дороже обходного («Прочее» на всё). **Главная мысль решения: честный путь должен стать дешевле обходного.** Система сама разводит позиции по документам и причинам, а «Прочее» становится дороже остальных причин.

## 1. Блок «Контекст» — персонажи и боли

| Роль | Где и как работает | Что ему важно | Боль (цитата) | Что из этого следует для дизайна |
|---|---|---|---|---|
| **Кладовщик** | Весь день, на ходу. Часто в подсобке с телефона/терминала, **одна рука свободна**, перчатки | Списать быстро и не забыть | «Пять документов из-за пяти причин — не буду» → всё в «Прочее» | Скан как основной ввод. Причина в одно касание и запоминается. Разбиение на документы делает система, а не он. Офлайн-очередь |
| **Старшая медсестра** | За компьютером. Отвечает перед проверяющими за учётные (ПКУ) | Учётный материал списывается только с причиной, серией и с её ведома | «Списали два флакона учётного вместе с бинтами как «Прочее»» | Учётный материал виден ещё на этапе поиска. «Прочее» для него запрещено. Серия и комментарий обязательны. Бой/утилизация уходят ей на подтверждение |
| **Бухгалтер** | Раз в месяц, отчёты | Причина → статья расходов | «Треть списаний — «Прочее»» | Причина одна на документ (из-за проводки). «Прочее» требует текстового пояснения. Метрика: доля «Прочего» |

**Вывод:** первичный пользователь экранов — кладовщик. Медсестра — контролёр, бухгалтер — потребитель результата. Интерфейс оптимизируем под скорость кладовщика, а контроль встраиваем так, чтобы он не замедлял обычный материал (их ~95 %).

## 2. Блок «Задача» — что сдаём

Три экрана как **один сценарий**:
1. **Форма списания** (десктоп 1440) — склад, материалы, количества, причина.
2. **Подтверждение** (десктоп) — сводка перед проведением.
3. **Быстрое списание** (мобильный) — 1–2 позиции у полки.
4. **Тупиковые состояния** — минимум 3 из 5, можно вайрфреймами. Важно, **что человек делает дальше**.

Явные требования к процессу: фиксировать допущения; если не уложились — написать, что отрезали. Объём **не** оценивается.

## 3. Блок «Бизнес-логика» — правила, разобранные по пунктам

### 3.1. Правила (как есть)

| # | Правило | Где проявляется в UI |
|---|---|---|
| R1 | Списание только с одного склада | Склад выбирается первым. Остальное заблокировано |
| R2 | Добавление: поиск по названию / артикулу / скан штрихкода | Единое поле поиска + сканер «слушает» всегда |
| R3 | Количество ≤ остатка | Валидация в строке |
| R4 | **Причина одна на документ** (проводка) | Поле на уровне документа |
| R5 | Причины: Выдано в кабинет / Срок годности / Бой и порча / Утилизация / Прочее | Сегменты/кнопки |
| R6 | «Выдано в кабинет» → обязателен кабинет | Появляется поле «Кабинет» |
| R7 | Учётный — из справочника | Метка в поиске и в строке (иконка + текст, не только цвет) |
| R8 | Учётный ≠ «Прочее» | Конфликт причины и состава |
| R9 | Учётный → обязательны серия и комментарий | Серия в строке, комментарий в подстроке |
| R10 | Учётный + Бой/Утилизация → подтверждение старшей медсестры **до проведения** | Отдельная ветка в подтверждении, резерв остатка |
| R11 | Неснижаемый остаток: списывать ниже нельзя | Колонка «Доступно» = остаток − неснижаемый |
| R12 | Просрочку списать в день обнаружения | Противоречит R11 |
| R13 | Проведённое не редактируется, отмена целиком — в тот же день | Окно отмены в подтверждении и после проведения |
| R14 | Отмена с учётным → подтверждение медсестры | Отдельный статус отмены |
| R15 | Мобильный: скан → кол-во → причина | Экран 3 |
| R16 | Связь пропадает на 1–2 мин: ввод не теряем, без серверной проверки остатка не проводим | Офлайн-очередь и проверка при синхронизации |

### 3.2. Найденные противоречия и как их решаем

| # | Противоречие | Решение (допущение) |
|---|---|---|
| **C1** | R4 «одна причина на документ» против реальности «весь день в один документ» | Документ = **одна причина** (проводку не ломаем). Но кладовщик не создаёт документы руками. На мобильном каждая позиция получает свою причину, а система сама собирает **документы дня по причинам**: «Выдано в кабинет 203 — 4 поз.», «Бой и порча — 1 поз.». На десктопе при конфликте одна кнопка выносит строки в соседний черновик |
| **C2** | R11 неснижаемый против R12 просрочки | **Неснижаемый остаток считается только по годным единицам.** Просроченные уже не «на остатке» по смыслу, поэтому их списание по причине «Срок годности» не нарушает правило: это предупреждение, а не ошибка. После проведения автоматически создаётся заявка на пополнение |
| **C3** | Учётный материал с телефона против «нельзя мимоходом» | Разрешаем, но честно: серия из DataMatrix или выбор из 1–3 серий на остатке большими кнопками. Комментарий — готовые формулировки + диктовка. «Прочее» скрыто. Бой/утилизация → на подтверждение. Честный путь ≈ 3 касания, обходного нет |
| **C4** | R10 «подтверждение до проведения» против «двадцать обычных + один учётный» | По умолчанию **разделяем**: обычные проводятся сразу, учётный уходит отдельным документом с той же причиной на подтверждение. Его количество **резервируется** (числится на остатке, но недоступно для других списаний) |
| **C5** | R13 «отмена в тот же день» против проведения в 23:50 | «День» = календарный день клиники (часовой пояс склада). В подтверждении показываем **сколько осталось до конца окна**. После окна — не отмена, а **корректирующий документ** «Сторно списания» со ссылкой на исходный (для учётных — через медсестру) |
| **C6** | R16 «не терять ввод» против «не проводить без проверки» | Офлайн-позиции живут в очереди на устройстве со статусом **«Не проведено — ждёт сети»**. При связи проводятся автоматически. Если сервер отказал — уведомление с готовым действием |

### 3.3. Что «намеренно не описано» — наши допущения

| Вопрос из задания | Допущение |
|---|---|
| Как и где медсестра подтверждает, сколько ждёт кладовщик | Входящие «На подтверждение» в веб-интерфейсе + push/уведомление. Цель SLA — до конца смены. Кладовщику ждать **не нужно**: документ висит в статусе «Ждёт подтверждения», количество в резерве |
| Медсестра недоступна (отпуск) | В справочнике ролей есть **заместитель** (назначается на период отсутствия). Запрос уходит тому, кто сейчас на дежурстве. Это видно ещё в подтверждении: «Получит: Петрова А.С. (замещает Иванову Н.П. до 28.10)» |
| Весь неснижаемый остаток просрочен | См. C2: списываем, предупреждаем, создаём заявку на закупку. Правило «держать просрочку нельзя» важнее |
| Разные причины в одном документе | Нельзя (проводка). Система раскладывает позиции по документам за пользователя (C1) |
| Кто заполняет серию, если она нечитаема | Кладовщик выбирает из серий на остатке (система знает их из приходов). Если выбрать нельзя — вариант «Серия нечитаема» + фото упаковки → **всегда** на подтверждение медсестре, она выбирает серию сама |
| Один склад у пользователя | Шаг выбора склада не показываем: склад виден как текст, без select |
| «Прочее» | Остаётся, но требует текстового пояснения (для бухгалтера). Для учётных недоступно |
| Комментарий у обычных позиций | Не нужен в строке. Есть общий комментарий документа |

## 4. Блок «Что нужно отрисовать» — разбор по экранам

### Экран 1. Форма списания (десктоп)

| Элемент | Решение | Состояния |
|---|---|---|
| Склад | Первым полем. Пока не выбран, поиск и таблица неактивны с подсказкой. Один склад → поле не показываем | не выбран / выбран / один склад (статично) |
| Причина | Сегменты (5 причин видно сразу, без раскрытия). «Выдано в кабинет» → поле «Кабинет». «Прочее» → поле «Пояснение» | пусто / выбрана / конфликт с учётными |
| Конфликт «Прочее» ↔ учётный | Не запрещаем молча. Показываем баннер с двумя выходами: **«Сменить причину»** или **«Вынести учётные (N) в отдельный черновик»** | а) учётные уже в таблице → выбирают «Прочее»; б) «Прочее» выбрано → добавляют учётный (предупреждение уже в результатах поиска) |
| Поиск | Одно поле: название / артикул / штрихкод. Сканер пишет в него всегда. Повторный скан = +1 к количеству | Результат: метка «Учётный», «Неснижаемый N», «Доступно X из Y», «Просрочено N», «Уже в документе» |
| Таблица | До 60 строк: липкая шапка, липкий итог, фильтр «С ошибками / Учётные», статус-колонка с текстом и иконкой. Подстрока у учётных: серия и комментарий | ок / ошибка / предупреждение / учётный |
| Итого | Позиций, сумма, учётных, из них на подтверждение | — |
| Провести / Черновик | «Провести» неактивна, рядом список **всех** причин блокировки со ссылками на строки | несколько причин одновременно |

### Экран 2. Подтверждение (модальное окно)

- Шапка: склад, причина, кабинет.
- Блок **«Спишется сразу»** и блок **«Уйдёт на подтверждение»** (кому, замещение, что с остатками: резерв).
- Выбор: «Разделить на два документа (рекомендуем)» / «Одним документом — всё ждёт подтверждения».
- Необратимость: «Изменить после проведения нельзя. Отменить целиком — до 23:59 сегодня (осталось …)». Если окно короче часа — жёлтое предупреждение.
- Результат: номера документов, статусы, кнопка «Отменить списание».

### Экран 3. Быстрое списание (мобильный)

- **Скан → карточка → количество (степпер, по умолчанию 1) → причина (последняя запомнена) → «Списать».** Обычный материал: скан + 1 касание ≈ 5–10 с.
- Цели нажатия от 56 px, основное действие внизу (зона большого пальца).
- Учётный: метка, серия из кода или выбор крупными кнопками, комментарий из готовых фраз, «Прочее» скрыто.
- Разные причины подряд → система раскладывает по документам. Кладовщик видит это в ленте «Сегодня» с группировкой по причине.
- Офлайн: «Сохранено на телефоне, проведём автоматически». Отказ сервера → уведомление с действием.

### Тупиковые состояния (делаем все 5)

| # | Ситуация | Что видит и что делает дальше |
|---|---|---|
| T1 | Просрочка ниже неснижаемого | Предупреждение, не блок. Списывает и получает автозаявку на пополнение |
| T2 | 20 обычных + 1 учётный, медсестра в отпуске | Разделение: 20 проводятся сразу, учётный уходит заместителю. Если заместителя нет, запрос уходит главной медсестре (эскалация) |
| T3 | Нет штрихкода, серия нечитаема | Поиск по названию → «Серия нечитаема» → фото → на подтверждение. Медсестра выбирает серию |
| T4 | Связь пропала после скана, коробка уже отдана | «Сохранено на устройстве. Проведём при связи — можно отдавать». Очередь, автосинхронизация, разбор отказа |
| T5 | Провели в 23:50, ошибку нашли в 09:00 | Отмены нет, есть «Сторно (корректировка)» со ссылкой на исходный. Профилактика: в 23:50 подтверждение предупреждает, что окно отмены — 9 минут |

## 6. Блок «Требования к дизайну» — чек-лист

- [ ] Понятно кладовщику без бухгалтерского опыта (причины человеческим языком, без «статьи 26»).
- [ ] Честный путь не дороже обходного.
- [ ] 1440 px. Мобильный: одна рука, перчатки, скан, цели ≥ 56 px.
- [ ] Ошибки: превышение остатка, неснижаемый, недопустимая причина, пустая серия. Текст = «что случилось + что делать».
- [ ] Учётный и статус строки читаются **без цвета** (иконка + текст + форма).
- [ ] Таблица на 60 позиций — главный акцент.
- [ ] Компоненты Figma с состояниями (строка, поле количества, бейдж, кнопка, результат поиска, баннер).
